# Scale My AI

You built something that works with AI. **What needs to change before 100,
1,000, or 10,000 people use it?**

Scale My AI is a small web app that assesses an AI prototype and returns a
plain-language **Scaling Report**:

- **What will break first** — ranked risks (exposed API keys, no auth,
  browser-only data, synchronous AI calls, …).
- **What to fix next** — a prioritised, do-this-first list.
- **Architecture at your scale** — an interactive slider (10 → 100 → 1,000 →
  10,000 users) that grows the recommended AWS architecture live.
- **Scaling roadmap** — Prototype → Shared App → Multi-user → Scalable AI →
  Governed AI.

It ships with a built-in **AI Assignment Grader** demo that runs entirely from
preloaded data, so a live presentation works even with no network or cloud.

> Free, self-hostable software. You deploy it into **your own** cloud account.
> No accounts, keys, or endpoints belonging to anyone else are baked into this
> repo.

---

## Rules first, AI second

The whole assessment is **deterministic and runs in the browser** — a rule
engine (`web/src/engine.js`) decides every risk, fix, roadmap stage, and
architecture diagram. That means:

- The app works with **zero backend**.
- Results are consistent and explainable — no hallucinated architecture.

The optional backend adds one thing: a friendly, plain-language **explanation**
of the findings, generated by **Amazon Bedrock** (default **Nova Micro**, with
**Nova Lite** as fallback). If the backend is absent or unavailable, the report
is still complete — the explanation button simply doesn't appear.

```
Browser (React SPA, deterministic engine)
   │  VITE_API_BASE (optional)
   ▼
API Gateway ──► Lambda ──► Bedrock   (explains findings only)
                   └──► DynamoDB      (daily AI budget counter)
```

## Repository layout

```
web/                  Vite + React frontend
  src/engine.js       the deterministic assessment engine (rules + architecture)
  src/App.jsx         the UI (landing, input, assessment, report + scale slider)
infra/terraform/      Terraform for the optional serverless backend + hosting
  lambda/index.js     the single backend handler (POST /analyze)

```

## Quick start (frontend only, no cloud)

```bash
cd web
npm install
npm run dev          # http://localhost:5173
```

With no `VITE_API_BASE`, the entire assessment works; only the optional AI
explanation is hidden.

## Full deploy (with the optional AI explainer)

Prerequisites: an AWS account, AWS CLI authenticated to it, Terraform ≥ 1.5,
Node ≥ 18, and **Bedrock model access** enabled for the models you pick
(Bedrock console → Model access). New AWS accounts may need to finish account
verification before Bedrock and CloudFront become available.

```bash
cd infra/terraform
cp terraform.tfvars.example terraform.tfvars   # edit if you like
terraform init
terraform apply

cd ../..
./scripts/deploy-frontend.sh                    # builds + publishes the SPA
```

`terraform apply` prints `api_base_url` and `site_url`. `deploy-frontend.sh`
reads those outputs, builds the SPA with the right API base, and publishes it.
Nothing is hardcoded, so the same commands work in any account or region.

### Hosting modes

`frontend_hosting_mode` selects how the SPA is served:

- `cloudfront` (default) — private S3 + CloudFront, HTTPS. Recommended.
- `s3_website` — public S3 website, HTTP only. Useful for accounts not yet
  verified for CloudFront.

## Configuration

### Frontend (`web/.env.local`, all optional)

| Variable          | Purpose                                          |
| ----------------- | ------------------------------------------------ |
| `VITE_API_BASE`   | Backend URL. Blank = fully static.               |
| `VITE_BRAND_NAME` | Wordmark shown in the header.                    |
| `VITE_CTA_URL`    | Optional link shown at the end of the report.    |

### Backend (Terraform — see `terraform.tfvars.example`)

| Variable                      | Default                  | Purpose                             |
| ----------------------------- | ------------------------ | ----------------------------------- |
| `aws_region`                  | `us-east-1`              | Region for backend + Bedrock.       |
| `bedrock_model_id`            | `amazon.nova-micro-v1:0` | Primary model.                      |
| `bedrock_fallback_model_id`   | `amazon.nova-lite-v1:0`  | Fallback model.                     |
| `max_ai_requests_per_day`     | `2000`                   | Daily cap on `/analyze` (then 429). |
| `lambda_reserved_concurrency` | `-1`                     | Optional spend cap (see notes).     |
| `api_throttle_rate` / `burst` | `20` / `40`             | API Gateway throttling.             |
| `allowed_origins`             | `["*"]`                  | Lock to your site origin in prod.   |
| `frontend_hosting_mode`       | `cloudfront`             | `cloudfront` or `s3_website`.       |

## Cost & abuse protection

Meant to be offered free to the public, so spend is guarded on several layers:

- **Daily budget counter** — `/analyze` returns 429 past the cap; the report
  still renders without the explanation.
- **API Gateway throttling** — steady-state + burst limits.
- **Cheap model by default** — Nova Micro.
- **Optional reserved concurrency** — bounds concurrent model spend (requires
  your account's concurrency limit to allow it).

---

## Security notes

- No provider API keys ever live in the frontend; model access is server-side
  via IAM.
- Pasted/described content is never executed.
- `terraform.tfvars`, `*.tfstate`, and `.env*` are gitignored — keep real
  account values out of version control.
- For a public deployment, review `allowed_origins` and consider AWS WAF in
  front of the API.
